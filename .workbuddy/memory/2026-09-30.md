## Agent 多轮运行自动重试优化（backend）

问题：多轮（工具循环）请求中，工具回灌的后续 LLM 调用一旦上游报错（如 5xx "internal server error"）就整条中断，无法自动重试。首次调用已有完整容错（流式回退、状态降级、多路由 failover），但中途调用没有。

修复（conversation 包）：
- 新增 `service_generation_retry.go`：`messageGenerationRunner.generateWithRetry` — 失败尝试无可见副作用且错误可重试（复用 `channel.ShouldFailoverRoute`：408/429/5xx/网络/EOF）时，同路由指数退避重试（默认 2 次，800ms*attempt，var 可测试覆盖），计入 maxLLMCalls 预算。
- `service_message_send.go` 工具循环两处 follow-up 调用改用 generateWithRetry。
- `service_temporary_tools.go`：runGenerate 增加 attemptObservableEvents 计数，新增 runGenerateWithRetry 闭包（同样口径），临时对话 follow-up/final 调用接入。
- 安全性：重试仅当失败尝试 0 可见事件（用量/思考/正文/工具），杜绝重复输出；取消与 4xx 不重试。
- 新增 `service_generation_retry_test.go`（fake llmGateway 单测）。

环境注意：本机无 C 编译器，`go test` 因 sqlite-vec cgo 依赖无法本地运行（CI 可跑）；构建用 `GOPROXY=https://goproxy.cn,direct CGO_ENABLED=0 go build`（默认 proxy 会 Bad Gateway，toolchain 需 go1.26.8）。

## 二次排查：internal.error 真因（18:50）

用户复测仍失败，且上游 API 后台只有一条成功请求 → 错误不是上游 LLM 返回的。证据链：
- 客户端收到 `internal.error`（未分类错误的兜底码）；若回灌 LLM 调用失败会包成 `upstream.unavailable`（502），可排除。
- 工具执行错误只变错误行不致命；trace 持久化失败只 Warn。
- 中断点在「工具执行后、回灌调用前」，该窗口唯一未包装错误路径 = `ensureFollowUpBudget`（billing DB 读写：EstimateUsageNanousd / RaiseUsageBalanceReservation）。
- 关键缺陷：StreamMessage/SendMessage 终态错误在服务端零日志，无法排查。

修复：
- `sendMessageInternal` 加统一 defer 错误日志 `conversation_message_send_failed`（trace_id/run_id/error_code/error_type/完整错误链）。
- SSE 终端事件 `internal.error` 附带 `detail` 字段（512 字符截断），业务错误不带。
- `ensureFollowUpBudget`（主路径+临时对话）套 `retryUsageBillingOperation` 瞬态重试。
- 工具循环回灌/最终综合失败加 Warn 日志。
- 新增 `TestStreamErrorPayloadInternalErrorCarriesDetail`。

下一步：用户需重新构建部署 backend，复现后看 docker logs 的 `conversation_message_send_failed` 或浏览器 Network 里 error 事件的 `detail` 字段，即可定位确切错误。

## 三次排查：真因找到 —— 项目工具 nil binding panic（19:33）

容器日志给出 panic 栈：`service_tool_execution.go:126 runtime error: invalid memory address or nil pointer dereference`。

根因：`executeAssistantToolCalls` 中 `binding := resolveMCPBinding(...)` 对项目工具返回 nil；守卫 `if binding == nil && !isProjectTool(...)` 让项目工具绕过 continue；随后 `row.MCPServerID = binding.ServerID`（MCP 服务器归属快照，近期新增）对 nil 解引用 → panic。**每次项目工具调用都在执行前崩溃** → gin recovery 吞掉 → 客户端只见 internal.error；panic 越过 sendMessageInternal 的 retErr defer（retErr 为 nil）所以无业务日志；上游只有第一轮一条成功请求。

修复（service_tool_execution.go）：
1. 归属快照加 `if binding != nil` 守卫 —— 直接修复 panic。
2. 新增 `executeToolCallSafely`（per-tool recover）：单个工具 panic 转为错误行回灌给模型，不再中断运行；调用点换用它。
3. 回归测试 `service_tool_execution_test.go`：项目工具无绑定不 panic（错误行 "project context is required"）；panic 转 tool error。

教训：go panic 会跳过 retErr 命名返回值赋值，defer 日志不会触发；SSE 场景 panic 被 gin recovery 变成流尾的 internal.error，与普通业务错误难以区分，必须看容器日志的 [Recovery] 栈。
