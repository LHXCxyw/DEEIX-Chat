# 8. Fork 同步上游按「补丁逐文件移植」，不做整仓 merge

Date: 2026-10-22

## Status

Accepted

## Context

本仓库是 DEEIX Chat 的个人 Fork，与上游官方版本相比，`apps/web` 与 `backend` 已有数百个文件的
二次开发差异（创作画布、项目工作区、消息回退、媒体重查等）。上游按小版本持续发布（0.4.5、
0.4.6……），每次都会带来少量 Web／后端修复、依赖与安全升级，以及与本 Fork 无关的桌面端发布
流水线改动。

若直接 `git merge upstream/main`：

- 上游每一个被 Fork 改过的文件都会变成冲突，冲突面覆盖整个二改范围，而不是上游真实改动的
  那几十个文件；
- 合并结果里「上游改动」与「Fork 二改」混在同一次合并中，事后无法区分某一行来自哪一侧；
- 上游桌面端流水线会随合并进入本仓库，而本 Fork 不发布桌面版。

## Decision

1. 同步以上游 tag 为基准，取 `git diff <旧tag> <新tag>` 作为唯一改动来源，按文件逐个落地。
2. 上游改过且 Fork 未改的文件直接取上游版本；两侧都改过的文件做语义合并：上游修复照收，
   Fork 二改保留。
3. 同步范围限定为 Web、后端、共享包与构建基础设施。桌面端不在维护范围，只由发布脚本保持
   版本字段一致。
4. 同步在独立的 `sync/web-backend-vX.Y.Z` 分支上分三次提交完成（依赖与安全升级、上游修复
   移植、版本与文档），验证通过后以 `--no-ff` 合回 `main`，保留「这是一次同步」的合并痕迹。
5. 版本号跟随上游对齐，不在 Fork 内单独维护一套版本序列。

## Consequences

- 收益：每次同步的改动量与上游真实改动成正比；冲突只出现在真正的重叠文件上；历史里能用
  `git log --first-parent` 看出每次同步对应的上游基线。
- 代价：不存在自动的合并基线，Fork 必须自己记录「当前对齐到哪个上游 tag」；每次同步都要人工
  判断重叠文件，无法依赖 Git 的三方合并。
- 已否决的备选：
  - 直接 merge 上游 tag——冲突面等于全部二改范围，且会把不维护的桌面端流水线带进来。
  - 定期 rebase 到上游——二改提交会被反复重写，远端已推送的历史无法安全变基。
  - 只 cherry-pick 上游提交——上游常以 merge commit 交付，单个提交粒度与文件范围不稳定，
    仍要逐文件核对，收益低于按 tag 求差集。
