# 7. 上游生成成功而产物待落盘时，运行仍记 success 且重查必须可用

Date: 2026-10-15

## Status

Accepted

## Context

视频任务的上游生成成功后，平台还要把视频从上游下载回来落成文件。这一步失败时（网络抖动、
上游 CDN 短暂不可用等可重试故障）平台的处理是：把保存职责移交输出节点，并通过
`media_artifact_pending` 事件通知前端「上游已生成、产物待重试」。此时运行被记为 **success**
（计费与统计的事实基础是「上游生成成功」），而 assistant 消息被标为 error。

但这条移交链路此前是断的：

1. 重查是回收产物的**唯一**入口，而它会拒绝 `status == "success"` 的运行，对外报
   `media.video_input_invalid`——于是「移交」变成了「死路」：用户看到失败，点重新查询得到
   「视频生成输入无效」。
2. 前端不认识 `media_artifact_pending` 事件，把它当未知事件直接终止流，节点显示
   `stream failed`；画布为此准备的待重试回调也从未被调用过。

两者叠加的结果是：一个「上游已经成功、只差落盘」的任务，在用户侧表现为看不懂的错误，
且无法回收。

## Decision

1. 保留「上游生成成功即运行 success」的口径，不因为产物落盘失败而改写运行状态。
2. 重查不再以运行状态作为拒绝条件：产物未落盘时它是唯一回收路径；产物已落盘时重查只会
   多下载一次，代价可接受。
3. 媒体任务的校验失败一律携带定位上下文（运行 ID、任务类型、协议、上游任务编号、运行状态），
   不再用「输入无效」这类无指向文案（与 ADR 0005 的 details 机制同源）。
4. `media_artifact_pending` 视为媒体链路的正式扩展事件：客户端必须注册它并把输出节点切到
   「保存待重试」，不得让未知事件终止整条流。

## 补充：回收路径不受「渠道启用状态」限制（同日）

重查与产物重试都靠 `BuildRouteForUpstream` 按上游 ID 定点重建路由。该方法此前会校验渠道
`status == "active"`，但**启用状态是给新请求路由用的门槛**：渠道一旦因失败被停用或降级，
上游已经跑完的任务就再也取不回来，对外还会退化成「路由未配置」。该方法只有重查/重试两个
调用方，不引入新流量，因此去掉该门槛（仍要求存在可用密钥）。

同时区分两种此前混为一谈的失败：

- `run.UpstreamID == 0`（个人模型路由不带平台上游 ID）→ 不报「路由未配置」，改为**按生成时
  同口径重新解析路由**（模型名 + 用户作用域 + 任务类型）。个人模型只有一条路由
  （`personalprovider.RouteResolver` 明确保证），因此不会选到别的上游；平台路由仍走
  `BuildRouteForUpstream` 定点重建，绝不负载均衡到别的渠道。
- 其余路由重建失败 → 保留原错误码，但附带运行上下文（含上游 ID）。

## Consequences

- 重查不再是"一次性探测"：上游返回 pending 时客户端进入**持续监听**（每 3 秒回查一次，
  节点回到运行态并显示上游进度），直到完成、上游判定失败、或再次超出 **10 分钟**等待上限
  （与生成期视频轮询预算同一口径），超时后仍保留"重新查询"入口。上游不上报进度的协议
  （xAI 视频）显示不确定态，不伪造百分比。

- 收益：长任务的回收链路真正闭环；「上游成功但没落盘」不再伪装成「输入无效」或 `stream failed`。
- 代价：允许对 success 运行重查，调用方理论上可以重复触发并产生重复文件。画布只在错误态或
  保存待重试节点上提供该入口，实际风险低；任务会话本身是软删除的一次性会话。
- 有意保留的不一致：同一任务下 assistant 消息为 error 而运行为 success。客户端以事件为准
  （`media_artifact_pending` → 保存待重试），不依赖运行状态推断产物是否可用。
- 已否决的备选：
  - 把「产物待落盘」记为 error——与「上游生成成功」的事实冲突，会让成功的上游调用被计为失败。
  - 维持「success 不可重查」——正是本次要修的死路。
  - 让前端在收到 `media_artifact_pending` 后改用消息兜底去捞产物——产物根本没落盘，
    消息里没有可捞的东西，仍然解决不了回收。
