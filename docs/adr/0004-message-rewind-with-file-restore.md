# 消息回退（Rewind）与文件状态联动

用户要求"回退到历史消息时文件变更一并回退"（对齐 Codex rewind 体验）。当前代码中 `WriteProjectFile` 覆盖同名文件时物理删除旧对象，文件历史不可恢复；工作区为项目级共享（一个项目下所有会话共用）。我们决定：**文件回退只保留一个入口——原会话内"回退到某条消息"（rewind），语义为时点快照**（整个工作区恢复到该消息完成时的状态，含覆盖其他会话此后的变更，回退前列出将被覆盖的变更供确认）；fork 维持只复制消息、不携带文件语义，避免在共享工作区上引入每会话独立文件视图。

## 落定决策

1. **回退入口**：原会话截断（rewind）。回退点之后的消息保留为非当前分支，可经分支切换找回；**文件跟随在"从非锚点分支继续发送"时生效**——前端提交前若发现目标父消息不是活跃锚点，先调用 rewind 恢复文件到该时点再提交；仅切换查看分支不自动改文件。
2. **版本留存**：新增文件变更日志表（path、before/after storage key、message_id、run_id）；`WriteProjectFile` / `DeleteProjectFile` 不再物理删除旧对象。日志按写入顺序（自增 id 升序）重放，不单独维护 seq 字段。恢复 = 沿日志推导目标时刻各路径应指向的 storage key，与当前文件表对账后落盘。整工作区 manifest 快照与 git 方案被否决（前者与变更日志重复，后者在对象存储上跑 git 不现实）。
3. **不可变版本**：旧版本对象全保留不 GC（对齐"原件一经写入永不原地修改"惯例）；GC 策略待真实存储数据出来再定。`project_workspaces.storage_bytes` 仍按活跃内容大小记账，版本副本占用不计入。
4. **回退可追溯**：rewind 自身记为一条特殊变更记录（来源=rewind，关联会话与目标消息），保证日志与文件实际状态始终一致、二次回退可推导。
5. **运行保护**：会话内存在 pending 消息（进行中的 run）时拒绝回退，提示先停止；不做自动停止。已知限制：工作区项目级共享，同项目其他会话进行中的 run 不在拦截范围内，项目级并发写保护留待后续。
6. **范围边界**：仅 3 个内置项目文件工具（write/patch/delete）可回退；用户在项目面板的写入/删除与 ZIP 导入同样入日志（来源 user/import），因此可回退；MCP 工具的文件操作无记录、明确不可回退。
7. **时点锚点**：T 取目标消息所属 run 的 `ended_at`（assistant 消息，仅落一次，不受用量/计费回写影响）；无 run 的消息退回创建时间。锚点分支自身的变更无条件纳入目标状态，不受 T 漂移影响。
8. **存量文件**：功能上线前写入、日志无记录的文件，回退时保持原样（保守策略：不可恢复也不误删），由实现注释与单测固化。

## Considered Options

- **fork 携带文件视图**：与共享工作区矛盾——要么 fork 时破坏性重置工作区，要么引入每会话版本指针（写时复制），后者牵动全部 7 个文件工具与前端文件树语义，改动面过大。否决。
- **仅撤销本会话变更（delta undo）**：多会话交错写同一文件时会产生"混合了未来变更的过去状态"，语义无法自洽。否决。
- **回退前检测其他会话变更即拒绝**：把高频场景变成死路，不如确认清单直接。否决。

## Consequences

- 恢复成本只与回退跨度内被触碰的文件数相关，与工作区总大小无关。
- "从非锚点分支继续发送"先恢复文件依赖第 4 条（回退事件入日志），实现时不可省略。
- 对象存储写入量上升（每次覆盖多留一份旧内容），属预期代价。
