# 消息回退（Rewind）与文件状态联动

用户要求"回退到历史消息时文件变更一并回退"（对齐 Codex rewind 体验）。当前代码中 `WriteProjectFile` 覆盖同名文件时物理删除旧对象，文件历史不可恢复；工作区为项目级共享（一个项目下所有会话共用）。我们决定：**文件回退只保留一个入口——原会话内"回退到某条消息"（rewind），语义为时点快照**（整个工作区恢复到该消息完成时的状态，含覆盖其他会话此后的变更，回退前列出将被覆盖的变更供确认）；fork 维持只复制消息、不携带文件语义，避免在共享工作区上引入每会话独立文件视图。

## 落定决策

1. **回退入口**：原会话截断（rewind）。回退点之后的消息保留为非当前分支，可经分支切换找回；切换分支时文件状态一并切到该分支时点。
2. **版本留存**：新增文件变更日志表（path、before/after storage key、message_id、run_id、seq）；`WriteProjectFile` / `DeleteProjectFile` 不再物理删除旧对象。恢复 = 沿日志推导目标时刻各路径应指向的 storage key，与当前文件表对账后落盘。整工作区 manifest 快照与 git 方案被否决（前者与变更日志重复，后者在对象存储上跑 git 不现实）。
3. **不可变版本**：旧版本对象全保留不 GC（对齐"原件一经写入永不原地修改"惯例）；GC 策略待真实存储数据出来再定。
4. **回退可追溯**：rewind 自身记为一条特殊变更记录（来源=回退事件，关联目标消息），保证日志与文件实际状态始终一致、二次回退可推导。
5. **运行保护**：存在进行中的 run 时拒绝回退，提示先停止；不做自动停止。
6. **范围边界**：仅 3 个内置项目文件工具（write/patch/delete）可回退；MCP 工具的文件操作无记录、明确标注不可回退。

## Considered Options

- **fork 携带文件视图**：与共享工作区矛盾——要么 fork 时破坏性重置工作区，要么引入每会话版本指针（写时复制），后者牵动全部 7 个文件工具与前端文件树语义，改动面过大。否决。
- **仅撤销本会话变更（delta undo）**：多会话交错写同一文件时会产生"混合了未来变更的过去状态"，语义无法自洽。否决。
- **回退前检测其他会话变更即拒绝**：把高频场景变成死路，不如确认清单直接。否决。

## Consequences

- 恢复成本只与回退跨度内被触碰的文件数相关，与工作区总大小无关。
- "切分支文件跟着切"依赖第 4 条（回退事件入日志），实现时不可省略。
- 对象存储写入量上升（每次覆盖多留一份旧内容），属预期代价。
